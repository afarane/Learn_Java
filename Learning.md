# Learning Log

A record of issues encountered while setting up and restructuring this project, why they happened, and how they were fixed.

| # | Error | Why it happened | Fix |
|---|-------|------------------|-----|
| 1 | *"Test.java isn't on the classpath, runtime may throw class not found"* | VS Code's Java debugger had no `launch.json`, so it didn't know how to resolve/run the class | Created `.vscode/launch.json` with a proper `mainClass` entry |
| 2 | *"Unsupported operation. Please use pom.xml file to manage the source directories"* | `java.project.sourcePaths` was set in `.vscode/settings.json`, but since this is a Maven project, the Java Language Server refuses IDE-level source-path overrides and insists Maven be the single source of truth | Removed the `settings.json` override; let Maven's `pom.xml` define source roots instead |
| 3 | Non-standard folder layout (`src/problems`, `src/tutorials` directly under `src`) | Maven's default convention is `src/main/java`; without it, Maven looks in the wrong place and finds nothing | `git mv`'d both folders under `src/main/java` to match convention (history preserved) |
| 4 | Package declarations no longer matched their folders (e.g. `package com.java.array;` living in `tutorials/com/java/array/`) | Java requires the `package` statement to mirror the physical directory path relative to the source root. Moving folders in #3 broke that relationship | Bulk-prefixed every affected file's package with `tutorials.` or `problems.` to match its new path; also fixed a `sed`-induced CRLF→LF line-ending side effect from the same edit |
| 5 | `git push` → *"Permission denied to testoasis"* (403) | Windows Credential Manager had a stale cached credential for account `testoasis` under `git:https://github.com`, which took priority over the correct `gh`-authenticated `afarane` account | Switched the active `gh` account to `afarane`, then deleted the stale Windows Credential Manager entry (`cmdkey /delete`) so Git fell through to the correct credential helper |
| 6 | VS Code Problems panel showing 78 problems, incl. *"var cannot be resolved to a type"* | `pom.xml` had no Java version configured, so Maven/the Language Server defaulted to an old source level that predates `var` (Java 10+) | Added `<maven.compiler.release>17</maven.compiler.release>` to `pom.xml`, matching the JDK VS Code actually runs |
| 7 | `UnsupportedClassVersionError: class file version 69.0 ... this JRE only recognizes up to 61.0` | Compiling manually with the ambient `javac` on `PATH` resolved to JDK 25, while VS Code launches classes with JDK 17 — a newer-compiled class can't run on an older JRE | Recompiled explicitly with the JDK 17 binary VS Code uses (`Microsoft/jdk-17.0.18.8-hotspot`) instead of relying on `PATH` |
| 8 | Remaining genuine warnings: raw-type generics (`LinkedList`, `Iterator`, `ArrayList[]`) | Old-style pre-generics code — legal but unsafe, since raw types skip compile-time type checking | Parameterized each: `LinkedList<Integer>`, `Iterator<Integer>`, `ArrayList<Integer>[]` (with a scoped `@SuppressWarnings("unchecked")` where a generic array literally can't be created in Java) |

**Net effect:** only 3 harmless, intentional warnings remain — a deliberate `finalize()` deprecation demo, a deliberate `10/0` divide-by-zero demo, and one javac-only rawtypes quirk the IDE itself flags as unnecessary to suppress. Everything else compiles and runs clean under JDK 17.
